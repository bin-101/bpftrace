# コーディングガイドライン

このドキュメントの目的は、どの言語機能を使用すべきか、使用すべきでないかについて共通の理解を確立することです。これにより、コードの読み取り、開発、レビュー時の精神的負荷を軽減できます。場合によっては、より一貫したユーザーエクスペリエンスの提供にも役立ちます。

このドキュメントに関する議論は、このドキュメントのテキストを変更するプルリクエストで行う必要があります。これにより、なぜそのようになっているのかを追跡し、参加するための構造化された環境を提供できます。

このドキュメントで言及されていない事項については、[C++コアガイドライン](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)に従ってください。つまり、このドキュメントはコアガイドラインよりも優先されます。

チェックインされたコードは、まだこれらのガイドラインに準拠していない可能性があることに注意してください。このドキュメントは新しいコードの参考として意図されています。理想的には、チェックイン済みのコードもこれらのガイドラインに従うように修正します（時間があるときに）。

## エラーハンドリングと例外

エラーが回復可能な場合（つまり、コードの下流の呼び出し元が選択的に処理、無視、またはさらに伝播できる場合）、関数の戻り値を通してエラーを渡します。

これに適した言語機能には以下があります：

* `std:optional`
* `int`
* `bool`

エラーが回復**不可能**な場合は、`FatalUserException`をスローすることを推奨します。例外は回復可能なエラーには使用**すべきではありません**。

### 例

回復可能なエラーの例は、マップへのエントリの書き込み失敗です。マップへの書き込みが失敗する理由は多数あり（マップが満杯、権限不足、マップがまだ存在しない等）、失敗時点では理由を確実に知ることができません。さらに、このタイプのエラーはプログラム全体を失敗させる理由にならない可能性があります。そのため、エラーを伝播する必要があります。

回復不可能なエラーの例は、`debugfs`がマウントされていない場合です。debugfsがマウントされていない場合、カーネルのデバッグ機能と対話できないため、すべてが台無しになります。そして、ユーザーの代わりにファイルシステムをマウントすべきではありません。そのため、失敗時点で例外をスローし、システムがbpftraceの準備ができていないことをユーザーに知らせるべきです。

## StructとClass

データを運ぶ受動的なオブジェクトにのみstructを使用し、それ以外はすべてclassを使用してください。

structのすべてのフィールドはpublicである必要があります。structは、異なるフィールド間の関係を意味する不変条件を持ってはいけません。これらのフィールドへの直接的なユーザーアクセスがそれらの不変条件を破る可能性があるためです。structには関連するメソッド（コンストラクタやデストラクタを含む）を持つべきではありません。

## 変数の命名

変数は`snake_case`（すべて小文字、単語間にアンダースコア）にする必要があります。

プライベートメンバーには末尾にアンダースコアを付ける必要があります。パブリックメンバーには末尾にアンダースコアを付けるべきではありません。

構造体のデータメンバーには末尾にアンダースコアを付けるべき_ではありません_。

例：

```c++
class Foo {
public:
  int snake_case;      // 良い
  int secondone;       // 悪い
  int var_;            // 悪い
  int camelCase;       // 悪い

private:
  int another_var_;    // 良い
  int private_var;     // 悪い
  int priv_;           // 良い
};

struct Bar {
  int var;             // 良い
  int tailing_;        // 悪い
};
```

## ログメッセージ

各ログレベルをいつ使用するかの詳細は以下の通りです：

- `DEBUG`: ログレベルに関係なく情報をログ出力；stdoutの使用と同様（ファイルと行番号付き）
- `V1`: 詳細ログが有効な場合のみ情報をログ出力（-v）；bpftraceの実行ごとに発生する可能性のある警告の出力に使用（BTFが利用できない等）
- `HINT`: ユーザーが遭遇した問題を解決する方法のヒントとなる情報をログ出力。通常、LOG(WARNING)やLOG(ERROR)の直後に使用される
- `WARNING`: bpftraceの動作や出力に影響する可能性があるが、実行の継続を許可する情報をログ出力；stderrの使用と同様
- `ERROR`: ユーザーが無効な操作を行ったことを示す情報をログ出力。これにより（最終的に）bpftraceが終了する（`exit(1)`経由）；これは主にコードベースの深い部分から`FatalUserException`をキャッチした後のmain.cppで使用される
- `BUG`: 内部的/予期しない問題（無効なユーザープログラムコードやCLI使用によるものではない）を示すために中止して情報をログ出力
